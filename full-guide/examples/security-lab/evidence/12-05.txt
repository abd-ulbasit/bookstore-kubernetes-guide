# Transcript for 12-kubernetes-for-machine-learning/05-notebooks-and-interactive.md,
# lab steps 0 to 8 (cluster), step 9 (image configs from the registries) and
# step 10 (the chart read offline).
# Tier A: a kind cluster that the lab owns. Kubernetes v1.37.0 server, kubectl
# v1.37.2, Helm v4.1.4, chart jupyterhub/jupyterhub 4.4.4.
# Recorded by running examples/security-lab/labs/12-05.sh from full-guide/, with
# VALUES set to a copy of the chapter's jupyterhub-values.yaml.
# The lab used its own namespace, p12-05-jupyter. The chapter names the jupyter
# namespace and applies the same manifests. Lines that name the lab namespace
# are kept as captured.
# The lab cluster has a different name from the guide's, and so does its node.
# The cluster's CNI is kindnet, which accepts NetworkPolicy objects but does not
# enforce them. No traffic was sent to test a policy.
# The hub was not installed in this run. Another install held the lab's
# heavy-install lock, so the chart was checked with a server dry run, and the
# hub and proxy Pods were not started. Nothing here shows them running.
# Step 9 reads each image's config through a registry API request, the anonymous
# manifest and config-blob requests. No image was pulled.
# Step 10 reads the chart offline with helm template. One maintainer email in
# the chart's metadata, in the helm show chart output of step 0, is redacted.
# What did not work the first time: the first attempt stopped at a shell syntax
# error before any command ran. The second attempt waited about two minutes on
# one API call in step 2 and then completed. After step 8, the admin identity
# was denied cluster-scoped reads and namespace reads. The reflector lines at
# the end are the client's watch errors from that. The namespace had already
# been deleted by step 8. Access returned later, and the admission gate was run
# against the lab cluster after that. The lab itself was not run again.
#
