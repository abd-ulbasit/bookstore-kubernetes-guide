# Tier A: a kind cluster named sf-sched on one Linux lab host. It has one
# control plane and two workers, each a Kubernetes v1.37.0 node, and the client
# is kubectl v1.37.2. The cluster is shared with other workers, so this run used
# its own namespaces, p04-03-bookstore and p04-03-team-a, where the chapter
# prints bookstore and team-a. Its PriorityClasses carry the prefix
# p04-03-bookstore-, where the chapter prints bookstore-. The lab node names
# (sf-sched-*) are kept as captured.
# The manifests are the chapter's own blocks, saved to files under the names the
# chapter gives. Each is applied through a sed expression that adds the prefix
# shown in the command. The Part 01 namespace bookstore is created here by a
# lab-only file, because this cluster has no earlier chapters. The filler and
# the vip are applied with the same text the chapter prints.
# The kind create step was not run: the cluster already existed. The config the
# chapter names is examples/security-lab/kind/cluster-three-node.yaml.
# The dry-run PriorityClass names (system-example, too-high, ceiling) are never
# created, so they carry no prefix.
# What did not work the first time: the first capture put only the two
# Bookstore classes in the quota. A probe then showed the system class accepted
# in the tenant namespace, so the quota was widened to the two system classes
# and the run was repeated. Two earlier runs also started while one worker
# carried a NoSchedule taint from another workload. The filler was then applied
# with one replica, and the run was repeated after the taint was gone. The
# first line of the run records the state it started in. The transcript below
# is the run that completed on a clean cluster, with two replicas.
# The cluster-wide list of PriorityClasses at the start can show objects that
# belong to other workers. This run changed only the p04-03 objects it created,
# and deleted only those.
# no worker carries another workload's taint at this point; the filler is applied with two replicas
