# kubectl v1.37.2, Helm v4.1.4. Chart chaos-mesh/chaos-mesh 2.8.7 (appVersion
# 2.8.7). Run on 2026-10-31 against the lab kind cluster sf-pilot.
# Two runs, in order: run A (namespace labels and server dry runs, no controller)
# and run B (the heavy install, the RBAC checks and the cleanup).
#
# Substitution: the chapter prints the reader's names. This run used these
# names in every command below and in the output:
#   bookstore              -> p11-07-bookstore (the Bookstore namespace)
#   chaos-mesh (namespace) -> p11-07-chaos
#   the values file        -> a copy whose targetNamespace is p11-07-bookstore
# The Helm release name stays chaos-mesh. The lab working folder is shown as
# lab/ in the file paths. The raw lines were kept, except that the client-go
# retry notices (18 lines per run, starting "I1031" and "Waited before
# sending request") were removed. No other line was changed.
#
# What ran:
#   - Run A: the namespaces, the label table, the chart rendered at 2.8.7 and
#     a server dry run of all of it (created nothing), and a server dry run of
#     experiment 10 (refused: no CRDs yet).
#   - Run B: the heavy lock, the chart installed, the daemon and the dashboard
#     Running, the controller Running after restarts, the daemon's privilege
#     read back, the three RBAC checks, server dry runs of experiments 30 and
#     40, and cleanup (the release, the CRDs, the namespaces).
#
# Not run, and why:
#   - Experiment 1 (pod-kill), experiment 2 (network delay) and experiment 3
#     (CPU stress) were not run. The catalog Pods never became Ready: postgres-0
#     stayed Pending while the lab control plane was unstable (kube-scheduler
#     at 0/1 with 52 restarts; apiserver and controller-manager restarting). The
#     chart's admission webhooks did not answer the server dry runs of the
#     experiment files, so those files were refused, not admitted.
#   - The Chaos Dashboard, the Workflow run and the SLO oracle were not run.
#     kube-prometheus-stack and metrics-server were not installed: the first is
#     heavy and both need cluster-scoped objects, and experiment 3 needs the HPA.
#   - The storefront, orders and payments were not deployed.
#   - No cloud resource was created.
#
# What did not work the first time:
#   - An early run A dry run into the chaos namespace (-n) was refused: the
#     chart renders the target-namespace RoleBinding into bookstore, and kubectl
#     with -n refuses objects from another namespace. That run was repeated
#     without -n, and each object keeps its own namespace.
#   - Run B's helm install reported a failure: the lab API connection dropped
#     (EOF and TLS handshake timeouts). The pods were created anyway and were
#     still starting. helm upgrade with the same values also reported failure
#     while the controller rolled over. The release then sat in "failed", and
#     later in "uninstalling", until the cleanup finished.
#   - The chaos-controller-manager crashed once at start, while its CRD watches
#     were still registering. It then ran.
#   - The pending postgres-0 was a control-plane problem, not a manifest one:
#     the scheduler did not process the Pod for several minutes.
#   - In run B, a heavy_unlock ran before the lock was confirmed as held by this
#     run. The lock belonged to another worker at that moment, so the unlock may
#     have released that worker's lock. This run then acquired the lock again for
#     the final cleanup and released it. The mistake is recorded here, not hidden.
