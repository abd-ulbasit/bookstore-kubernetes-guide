# Transcript for 06-production-readiness/04-autoscaling.md, hands-on steps 0 to 4.
# Tier A: kind clusters, Kubernetes v1.37.0 nodes, kubectl v1.37.2 client,
# Helm v4.1.4. Recorded in two sessions against shared kind lab clusters. The
# lab clusters' names are not the chapter's `kind-bookstore`.
#
# First recording (from "## step 0" to the line "## second recording"): a
# single-node cluster named sf-pilot-control-plane. Namespace substitution: the
# chapter's `bookstore` is `p06-04-bookstore` in this recording, and `keda` is
# `p06-04-keda`. The manifests were applied from copies with only the
# namespace names changed. A path in a working copy is written as its
# repository path, examples/bookstore/raw-manifests/. Terminal colour codes
# are removed. A local API tunnel address is written as <port>. Nothing else
# is edited.
#
# Second recording (from "## second recording"): a three-node cluster, shown as
# sf-sched-control-plane and two workers, with about 3 GiB of host memory to
# spare and a slow disk. It ran the script examples/security-lab/labs/06-04.sh
# one phase at a time (metrics, bookstore, spread, idle, load1, then cleanup),
# each phase in one foreground command, and used the chapter's own namespace
# names, bookstore and metrics-server, with no substitution. The metrics-server
# chart is 3.14.0 (app v0.9.0). The Bookstore manifests were applied through a
# link named examples/bookstore/raw-manifests, so the commands read as in the
# chapter. The edits to the recorded lines are these: the script's own stop
# message at the end of the bookstore phase is removed, and the two sections
# headed "step 0e (continued)" and "abort" were run by hand between phases
# and are placed where they ran. Terminal colour codes are removed.
#
# What did not work the first time, first recording:
# - 12-redis.yaml was missing from the first apply, so catalog's /readyz failed
#   on Redis and its rollout hit the progress deadline. Applying Redis fixed it.
# - The first apply of 19-payments-worker-deploy.yaml and one rollout check
#   lost the API connection (EOF). Both were re-run.
# - The resource metrics API (v1beta1.metrics.k8s.io) was registered to another
#   worker's metrics-server, which had no endpoints. The HPA therefore reported
#   <unknown> for CPU and never scaled (step 2).
# - No install lock could be taken for KEDA (another worker held it), so KEDA
#   was not installed. Step 3 renders the chart and dry-runs it instead.
# - The KEDA test namespace stayed Terminating after its delete, because the
#   stale v1beta1.metrics.k8s.io discovery failure blocks namespace deletion.
#   The namespace was left to finish once the discovery failure clears.
#
# What did not work the first time, second recording:
# - The metrics phase's log read right after the install showed only informer
#   lines. The refusal had been logged just before them, and the capture headed
#   "step 0e (continued)" reads it from the same pod after the fix.
# - The Bookstore phase stopped at its wait for the catalog rollout. The third
#   catalog replica stayed Pending: catalog spreads over kubernetes.io/hostname
#   with DoNotSchedule, and the tainted control-plane node counts as an empty
#   domain, so each worker may hold one replica. The spread phase shows the
#   event and patches nodeTaintsPolicy: Honor on the Deployment in the cluster
#   (the shipped file is unchanged), and the rollout then completed.
#   The wait for the rollout moved from the bookstore phase to the spread
#   phase in the committed script after this run.
# - The load phase did not finish. About 75 seconds in, the host's load average
#   was near 30 on four cores, API answers slowed (one sampling pass took about
#   two minutes and `kubectl top` answered "Metrics API not available"), and
#   kube-controller-manager and kube-scheduler restarted once each. Before this
#   run they already showed 38 and 40 restarts in about ten hours, and the
#   kube-apiserver 17. Under the rule for this lab, the Job was deleted and
#   everything the run installed was removed. The controller-manager and the
#   scheduler restarted once more during the removal.
#
# Not run in this transcript: the scale-out of catalog under load, the lowered
# CPU target, the hold at maxReplicas and the scale-in after the load, and the
# load tests of the KEDA scaler. KEDA was not installed. The resource metrics
# API was served only from the metrics phase to the cleanup phase of the second
# recording.
