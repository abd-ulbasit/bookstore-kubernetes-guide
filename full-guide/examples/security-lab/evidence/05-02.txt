# Transcript for 05-security/02-pod-security.md, hands-on steps 1 to 10.
# Tier A: a kind cluster, Kubernetes v1.37.0 node, kubectl v1.37.2.
# Node runtime: containerd v2.3.4, runc 1.4.3, crictl 1.36.0.
# Recorded by running examples/security-lab/labs/05-02.sh from full-guide/.
# The cluster name is shown as `security-lab`.
#
# What did not work the first time: user-namespace Pods (hostUsers: false)
# never start on a default kind cluster. The kube-apiserver accepts the field,
# but the kubelet cannot create the sandbox because the kind node is itself a
# container and the nested read-only sysfs mount is denied. That is why 01.01
# keeps hostUsers out of the baseline until it is verified, and why this lab
# shows what the field would do rather than claiming it runs here.
## step 1 — one namespace that permits everything, one that enforces restricted
$ kubectl create ns psa-lab && kubectl label ns psa-lab pod-security.kubernetes.io/enforce=privileged
namespace/psa-lab labeled

$ kubectl create ns psa-restricted && kubectl label ns psa-restricted pod-security.kubernetes.io/enforce=restricted pod-security.kubernetes.io/warn=restricted
namespace/psa-restricted labeled
